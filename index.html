Understanding RL_in_AD: from noisy GPS to a sequence of roads

This project learns useful representations of roads and vehicle movement, then combines those predictions with geometry to match GPS traces to roads and predict likely next road segments.

Its central model comes from the RSSM and Dreamer family, but the application is different: the model assigns road segments; it does not steer, accelerate or brake a real vehicle. The repository contains both the current matching interface and earlier research experiments. This guide separates them.

Explained from source revision 951a4ad. Code behavior is distinguished from reported experiments; training runs and absent checkpoints have not been reproduced for this guide.

1. What problem does it solve?

Imagine a taxi travelling on a main road beside a narrow parallel street. GPS noise sometimes places its dots nearer the wrong street. Assigning every dot to the nearest road can produce an impossible route that jumps between disconnected roads.

Map matching asks which road segment the vehicle was probably on at each recorded fix. It uses distance, direction, road connections and the history of movement. Path prediction starts from the observed history and asks which road segments may come next.

TaskInputOutputExample
Offline map matchingA recorded GPS trajectory and a city road graphA road-segment assignment for each fixRecover a plausible route after the taxi trip has finished.
Online matching interfaceA GPS sequence, processed with sequential matching decisionsOne road assignment at each stepEstimate the current road. The present implementation has a lookahead qualification explained below.
Path predictionObserved GPS history and graph connectivityA sequence of predicted future segment IDsPredict likely next roads; this is not an exact arrival-time or latitude/longitude forecast.

The research explored reinforcement learning (RL) and imitation/weak supervision (IL). The documented useful matching system is a hybrid of the world-model road head and geometric decoding. The optional RL actor is a different experimental component, not the engine loaded by the current Matcher API.

2. From GPS fixes to model inputs

  1. Parse raw trajectories. Source-specific parsers handle Porto, T-Drive and GeoLife formats. The shared representation contains trajectory IDs, latitude, longitude, timestamps and sequence positions.
  2. Clean and split trips. Remove unusable fixes and implausible jumps; derive time gaps, travelled distance, speed and bearing. Defaults include a 55 m/s speed threshold, splitting at gaps above 180 seconds, and at least five points per retained segment. Write processed Parquet data and a manifest.
  3. Build a road graph from OpenStreetMap. A directed road network describes segments and legal connections. A second, “line” or “dual” graph turns road segments into nodes; edges then represent possible segment-to-segment turns. This is the graph the road encoder uses.
  4. Retrieve candidate roads for each fix. Project geometry into a metric coordinate system and search nearby segments. Defaults are at most ten candidates within 50 metres. Record perpendicular distance and road attributes. Invalid padded slots use masks and a segment ID of −1.
  5. Batch sequences. Assemble GPS features, candidate segment IDs, geometry, graph embeddings and validity masks. Stage 1 has a 128-fix sequence cap; training later uses shorter windows and a curriculum.

A candidate set is a shortlist, not a correct answer. If the true road is absent from the shortlist, the classifier cannot select it. Metric projection also matters: a threshold in metres cannot be applied directly to longitude degrees.

The line graph is useful because the question is “which road can follow this road?” In contrast, the primal road graph keeps intersections as nodes and supports geometric route-distance calculations.

3. What each neural component does

The project has two encoders before the world model. “Transformer encoder” and “recurrent world model” are not competing descriptions: the transformer builds observations, and the RSSM carries state through time.

ComponentPlain-language jobInputs and outputs
RoadGATDescribe a road using both its properties and neighbouring roads.13 numeric road features plus a learned highway-category embedding → two graph-attention layers → a 256-number road embedding.
GPS/road encoderCombine where the vehicle was observed with which roads are nearby.Relative GPS coordinates, direction, log speed/time gap, positional/hour/weekday embeddings, and candidate road tokens → transformer representation z1, width 256.
RSSM memory hCarry information from earlier steps and road assignments.Previous memory, previous stochastic state and a previous road embedding → GRU memory, default width 512.
RSSM stochastic state zRepresent the current situation with discrete, sampled latent variables.Default 16 groups × 16 categories; concatenate one selected category per group into 256 entries. Larger runs can use 32 × 32.
Prior and posteriorPredict without the current observation, or infer after observing it.Prior uses h; posterior uses h plus z1. The redesigned RSSM2 adds normalization inside these networks.
Road headScore the actual candidate road segments.Full state (h,z) and candidate road descriptors → candidate scores. Invalid candidates are masked. The head is shared across candidates, not a fixed “road 1…road N” city-wide classifier.
GPS, speed and reward headsMake the latent state useful for movement and road selection.The redesigned GPS head reads z only; speed reads (h,z); the reward head also uses candidate-road information.

Do not confuse z1 with z. z1 is the encoder’s observed-feature vector. z is the sampled stochastic component inside the RSSM. The full recurrent state is (h,z).

The GPS encoder sees candidate distance, but the world-model road head does not directly receive perpendicular distance as one of its candidate key inputs. Explicit geometric emissions are added later in hybrid matching. This helps explain why combining the learned score with geometry can improve the result.

4. Follow a model step

Use the buttons to follow observation, imagination and route decoding. This is a conceptual walkthrough, not a running trained model or a display of measured scores.

Observe: use the real GPS evidence

Update memory using the previous state and road embedding. Encode the current GPS context and candidates into z1. The posterior combines h and z1, then samples z. Heads read the resulting state. During training, compare the prior and posterior with KL divergence; the comparison is a loss, not another observation input.

Imagine: continue without a future GPS fix

Advance the GRU with the last state and selected road embedding. Sample the next z from the prior. Score possible next roads and choose one, then repeat. The production predict method obtains candidates from graph successors plus the current road. Some research evaluations and actor-training rollouts instead use candidate sets extracted from recorded future GPS, so those settings must not be confused.

Decode: combine predictions with road geometry

The road head produces preferences, not a guaranteed connected route. Offline hybrid matching adds geometric evidence and uses Viterbi to find a good sequence across a chunk. Online mode makes sequential decisions with geometry/topology terms. Neither operation is PlaNet’s CEM search or the experimental RL actor.

5. How the project learns

“No human labels” does not mean “no supervision.” The system learns from masked coordinates, future coordinates and geometrically generated road targets. A pseudo-label is an automatically generated estimate of the answer; it can be wrong. The main road-head training differs from the later reward-based RL experiment.

StageWhat changesTraining signalWhy it exists
0 · Road encoderTrain RoadGAT.Contrastive learning on two perturbed views of the graph.The same road should have a consistent representation even when some features or edges are hidden.
1 · GPS/road encoderTrain Stage1Encoder with frozen road embeddings.Recover masked GPS; predict next coordinates; fit soft candidate-road targets based on distance.Learn useful observation features before training dynamics.
2 · Legacy reconstruction modelTrain the earlier RSSM and larger decoder.GPS reconstruction, a mixture-density residual decoder, speed/road objectives and KL.Preserved experimental lineage. This is not the redesigned default architecture.
2R · Decoder-light world modelTrain RSSM2 and HeadsLight; observation encoder stays frozen.GPS, speed, posterior/prior road losses, predicted physics reward, balanced KL.Learn road-relevant latent dynamics while reducing reconstruction shortcuts.
Optional relabeling / self-trainingCreate geometric Viterbi expert targets and blend them into training; optionally use model-chosen previous roads.Expert pseudo-labels and scheduled sampling.Improve targets or expose training to the model’s own previous mistakes.
3 · Optional actor–criticFreeze world model; train actor and critic.Predicted rewards and lambda-return advantages during imagination.Test whether a road-choice policy improves on the direct road head. It is not required by the Matcher API.

The Stage 2R objective in ordinary language

GPS error + speed error + posterior road error
+ 0.5 × prior road error + reward error + balanced KL

The GPS head reads only the stochastic state, to encourage that state to contain spatial information. The road targets are soft probabilities derived from perpendicular distance, with a default 10 m scale. The prior-road loss trains road prediction without the current observation. The reward head learns a compressed symlog version of the physics reward.

Balanced KL has two gradient paths: a dynamics term teaches the prior to match the posterior, and a representation term regularizes the posterior toward the prior. One side is held fixed for each term. The code weights these paths separately and applies a per-group free-bits floor. A nonzero minimum KL loss alone therefore does not prove the latent state is informative.

What the physics reward encourages

TermIntuitionDefault weight
DistancePrefer roads near the GPS point: −distance / 10 m.1.0
HeadingPrefer a road direction consistent with movement.0.5
One-way legalityPenalize assignment against a one-way road’s direction.1.0, with a 5-point violation penalty
SpeedPenalize speed above a known road limit.0.3
TopologyPrefer staying on the same or an adjacent segment.2.0
SmoothnessPrefer road turns consistent with the GPS turn.0.2

These are designed rules, not human-verified driving rewards. A policy can improve its score under the learned reward model without becoming a better map matcher. That distinction is central to the negative RL results.

Training settings, capacity and optional switches

Default Stage 2R settings include 200,000 trajectories, batch 16, 40,000 steps, learning rate 10−4, and a sequence curriculum from 16 to 64 fixes after 10,000 steps. Defaults are not the configuration of every reported run: the logs also describe larger datasets and 32 × 32 latent states.

Scheduled sampling can substitute the model’s previous road choice for the pseudo-labeled previous road. Viterbi targets can be mixed with distance targets; both are disabled by default. Multi-city mode shares neural modules while swapping city-specific graph/data inputs. The optional encoder-unfreezing switch targets RoadGAT in single-city training; it does not unfreeze the GPS transformer.

Stage 3 uses REINFORCE, a critic and lambda-returns, with a default 15-step imagination horizon. Its future candidate lists come from recorded trajectories. This constrains the imagination setting. Also, its actor/critic constructor uses the default stochastic width; support for larger-latent checkpoints should be checked before using that entry point.

6. Matching and prediction after training

Offline: hybrid emissions and Viterbi

An emission measures how plausible a candidate road is for the current observation. Geometric emissions prefer nearby roads; the learned road head adds context. A transition score measures whether moving between candidate roads is plausible, using road-network travel distance and observed movement.

Viterbi uses dynamic programming to find a high-scoring sequence of assignments. It is allowed to use observations later in the recorded chunk. In this implementation, decoding restarts at each 128-fix chunk, so it is not one globally optimized route across an arbitrarily long trip.

Online: sequential decisions, with an implementation qualification

The trained-city default is hyb+topo: learned and geometric scores plus a topology term, with resets for large GPS gaps or missing candidates. However, Stage 1 first encodes the whole chunk with unmasked temporal attention; the gap threshold also uses the chunk’s median time interval. Earlier decisions can therefore depend on later input within the chunk. Sequential RSSM output is not the same as an end-to-end strictly causal streaming system.

Prediction: roll the prior over graph successors

predict warms up on the last observed window, then rolls the prior forward. Each future step considers graph successors of the previously chosen segment, plus staying on that segment. It returns segment IDs for a chosen number of future steps. The API does not return calibrated route probabilities, predicted travel times or a generated future GPS trace.

The geometry fallback is a rule, not an OOD detector

The current code has TRAINED_CITIES = {"porto"}. Unlisted cities default to the geometric nk mode. This is a manually configured city rule, not a learned test that decides whether an observation is out of distribution.

The standalone geometric baseline can operate without training a world model. But the Matcher constructor eagerly loads neural checkpoints even when its selected matching mode is geometric. “Zero-training baseline” should not be read as “every Matcher call works without checkpoint files.”

7. How the project connects to RSSM, PlaNet and DreamerV3

RSSM is an architecture. PlaNet and DreamerV3 are complete agents that use world models. This project adapts that architecture to GPS and roads; it is not a complete reproduction of either agent.

ConceptPlaNet / DreamerV3RL_in_AD adaptation
ObservationImages in the original PlaNet experiments; Dreamer supports sensory observations.A transformer representation of GPS history and nearby road features.
Deterministic memoryRecurrent state h summarizes history.GRU memory; the transformer does not replace this recurrent dynamics component.
Stochastic statePlaNet uses Gaussian latents; DreamerV3 uses categorical representations.Categorical groups with straight-through sampling, in the Dreamer lineage.
Prior / posteriorPredict without a new observation; infer using the observation.Same distinction, conditioned on GPS/road embedding z1 instead of an image.
Transition/actionPrevious state and environment action advance the model.A road-segment embedding acts as the action input. It is a chosen/pseudo-chosen road, not a motor command.
Observation modelAn image decoder supplies reconstruction training signal.Legacy reconstruction-heavy decoder; redesigned model uses smaller GPS/speed heads, with GPS depending only on z.
Reward / continuationDreamerV3 predicts reward and episode continuation; uses distributional learning techniques.Candidate-conditioned, symlog-regressed physics reward. These model classes do not have DreamerV3’s continuation head or a full matching distributional reward/value implementation.
Choosing actionsPlaNet uses CEM; DreamerV3 learns actor and critic from imagined experience.Stage 3 experiments with actor–critic. The current matching API uses a road head with geometric/Viterbi decoding.

Viterbi and CEM solve different problems. Viterbi decodes a plausible assignment sequence for recorded observations. PlaNet’s CEM searches future action sequences for high predicted reward. Calling the project’s Viterbi matcher “PlaNet planning” would hide this distinction.

DreamerV3’s published actor loss uses REINFORCE for both discrete and continuous actions. The project’s Stage 3 likewise trains a road-choice actor with a score-function estimator and a critic, rather than differentiating actor actions through frozen model dynamics. But its candidate construction and reward design are application-specific.

8. Concepts that make the code easier to read

Attention, graph attention and road tokens

Attention lets a representation weigh other inputs. Temporal attention relates GPS fixes to one another. Cross-attention relates a fix to candidate roads. Graph attention relates a road segment to connected segments. A token or embedding is simply a learned vector used by these operations, not a word or a manually named physical variable.

Categorical latents and straight-through gradients

Each latent group selects one category. The forward pass uses a hard one-hot representation. Because a discrete selection is not ordinarily differentiable, the backward pass uses a differentiable soft-probability surrogate. This is a training approximation. A 32 × 32 state means 32 groups with 32 alternatives each, not 1,024 independent binary switches.

Posterior collapse and the decoder-light redesign

If a powerful deterministic path can reconstruct observations by itself, the stochastic latent variables may contribute little. A low reconstruction error can then coexist with an unhelpful latent state. The redesign removes the mixture-density reconstruction burden and makes GPS prediction depend on stochastic z. This encourages information to pass through z; it is a design response, not a mathematical guarantee that collapse is eliminated.

KL divergence, free bits, symlog and lambda-returns

KL measures a difference between probability distributions. Free bits/nats avoid penalizing very small KL values below a chosen floor, leaving some representational capacity unpenalized. Symlog compresses the magnitude of positive and negative targets while keeping their sign. Lambda-returns combine short and longer reward lookahead with a critic’s value estimate to train behavior.

Weak supervision, imitation and scheduled sampling

A geometric or Viterbi estimate can serve as a pseudo-label instead of a human label. Learning to reproduce it is weak supervision or imitation of an expert estimate. Scheduled sampling changes which previous road is fed to the recurrent model, gradually allowing its own predictions. The optional expert blending here is not proof of the full performance guarantees associated with general DAgger algorithms.

Why optimizing reward may worsen the real task

The learned reward is only a proxy for correct road matching. An actor can discover choices that the reward predictor overvalues. Predicted return may rise while evaluation agreement falls. The project’s failed RL experiment is a practical example of this proxy-optimization problem, often described using Goodhart’s law.

HMM, geometry and future-information leakage

An HMM combines per-observation emission evidence with transitions between hidden road states. Viterbi finds a best sequence under those scores. It uses more than nearest-road snapping. A comparison becomes misleading if a method intended for live use can see future observations, or if test trajectories were included in training. Both the input window and the data split must be checked before interpreting an accuracy number.

9. Reported results: read the metric before the number

The repository is an engineering research log, with useful positive and negative results. The figures below are reported results from that log, not newly rerun experiments or proof of deployed production performance.

What “Hit@1” means here

In the inspected Porto evaluator, a chosen road is a tolerant hit if its perpendicular distance to the GPS fix is within 5 metres of the nearest candidate’s distance. This is a geometry-based proxy, not human-verified road identity. Prediction labels hit@1, hit@5 and hit@15 refer to future step horizons, not top-1/top-5/top-15 candidate accuracy.

Three checks needed before making a strong generalization claim

  1. Independent test split. The default 200k prefix avoids the evaluator’s next 500 indices, but increasing the training limit or loading the whole pool does not visibly exclude them in the loader. Without an external split manifest, full-pool held-out independence is unverified.
  2. Available information. Some prediction evaluation rollouts retrieve candidates from the real future GPS fixes. That is easier and different from the production predictor, which must use graph successors without future GPS.
  3. Reference quality. Tolerant geometric scores, HMM/expert agreement and human road ground truth answer different questions. Always state which reference was used.

10. How to use the repository

The Git repository contains source and research notes. Datasets, processed city graphs and trained checkpoints are not bundled. Cloning it is not sufficient to reproduce the reported experiments. The named checkpoint aliases refer to files that must exist locally.

git clone https://github.com/Vineet5-Data/RL_in_AD.git
cd RL_in_AD
python -m venv .venv
# Activate .venv using your operating system's normal command.
python -m pip install -r src/requirements.txt
cd src

# Inspect supported arguments before selecting your data paths.
python -m preprocessing.preprocess --help
python -m roadgraph.run --help
python -m training.stage0 --help
python -m training.stage1 --help
python -m training.stage2r --help

Core dependencies are PyTorch, PyTorch Geometric, NumPy/Pandas/PyArrow, NetworkX, GeoPandas and OSMnx. Choose a PyTorch build suitable for your hardware. CPU availability does not mean a large training run is fast.

Once those artifacts are present, the public API takes aligned arrays of latitude, longitude and Unix timestamps:

from matcher import Matcher

matcher = Matcher(city="porto", ckpt="final")
offline_segments = matcher.match_offline(lat, lon, t)
online_segments = matcher.match_online(lat, lon, t)
next_segments = matcher.predict(lat, lon, t, horizon=15)

Matching returns integer segment IDs, with −1 for unmatched entries. IDs are local to the prepared graph; they are not universally transferable road identifiers. horizon=15 means fifteen predicted steps, not fifteen seconds.

Set explicit paths rather than assuming every script shares the same working-directory defaults. Start with a small preprocessing sample or graph test tile, inspect the artifacts, then train in dependency order. The repository’s self_guide.md records environment-specific workflow commands; it is a run reference, not a portable guarantee that all paths or checkpoints exist on another machine.

12. Read the project alongside the papers

  1. First understand the full state: deterministic memory plus stochastic state. Then inspect the project’s GRU and categorical prior/posterior.
  2. Understand transition, inference, observation and reward models. Then see which project head replaces each role.
  3. Understand reconstruction and KL training. Then compare Stage 2 with the decoder-light Stage 2R changes.
  4. Understand PlaNet’s CEM planner. Then distinguish it from project Viterbi matching and graph-based prediction.
  5. Read DreamerV3’s world model and actor–critic learning. Then inspect optional Stage 3, remembering its candidate-conditioned rollouts and different reward/value implementation.

The repository’s wider literature covers HMM map matching, trajectory encoders, vectorized road graphs, posterior collapse, weak supervision, decoder-free/light world models and data scaling. Those topics explain the design choices; their presence in a literature directory does not mean every referenced method is implemented.
